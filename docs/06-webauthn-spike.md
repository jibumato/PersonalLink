## 2. 検証済み(自動テスト green)

`web/tests/webauthn-spike.spec.ts` — Playwright の CDP Virtual Authenticator を使用。

```
✓ 対応状況が検出される
✓ Passkeyを作成し、ID入力なしで再認証できる
✓ 未登録の端末ではログインできない
✓ ヘルスチェックがRP IDを返す
  4 passed
```

**この成果の意味**: WebAuthn は「実機でしか確認できない」と思われがちだが、**登録・認証のプロトコル部分は CI で回帰テストできる**。

→ ROADMAP のリスク「1人体制での実地テスト負荷」が下がる。実機確認は**「本当に Face ID / 指紋のダイアログが出て通るか」の一点**に絞れる。

### 仕様との対応

| 仕様の要求 | スパイクでの確認 |
|---|---|
| A-3「パスワードは作りません」 | パスワード入力欄が存在しない構成で登録が完結 |
| A-1「ログイン」ボタン1つで済ませたい | `allowCredentials: []` + `residentKey: "required"` で **@ID入力なしログイン**が成立 |
| 憲法第二条(最小収集) | `attestationType: "none"` — 端末を識別しうる情報を受け取らない |

## 3. 未検証(オーナーの実機が必要)

以下は**人間が実機で触らないと分からない**。S1 開始前、または S1 冒頭で実施する。

### 実施手順

1. `web/` をステージング(HTTPS の固定ドメイン)へデプロイする
2. 実機のブラウザで `https://<ステージング>/spike/webauthn` を開く
3. 画面の手順1〜3をそのまま実行する

### 確認したいこと

| # | 確認項目 | なぜ重要か |
|---|---|---|
| 1 | iOS Safari で Face ID / Touch ID のダイアログが出て登録できるか | 日本の主要ユーザー層 |
| 2 | Android Chrome で指紋 / 画面ロックで登録できるか | 同上 |
| 3 | **ブラウザを完全終了してから**ログインできるか | 「また使うか」= 再利用率 KPI に直結 |
| 4 | 種別が `multiDevice`(同期される)か `singleDevice` か | multiDevice なら機種変更で Passkey が引き継がれる。**リカバリーコードの重要度が変わる** |
| 5 | iOS のプライベートブラウズで動くか | 動かない場合の案内文が必要 |
| 6 | Conditional UI(入力欄からの自動サジェスト)が使えるか | 使えれば A-1 のログイン体験がさらに短縮できる |

**特に #4** は仕様に影響する。`multiDevice`(iCloud キーチェーン / Google パスワードマネージャで同期)が既定なら、「端末を失くしてもリカバリーコードなしで復帰できる」ケースが多くなり、A-3 のリカバリーコード保存強制の文言をやわらげる余地が出る。逆に `singleDevice` が多いなら、**複数端末への Passkey 追加をオンボーディングで強く促す**必要がある。

## 4. 発見: RP ID とドメインの依存(**計画変更が必要**)

> **Passkey は RP ID(ドメイン)に紐づく。RP ID を変えると、既存ユーザーの Passkey は全て無効になる。**

これは仕様や実装の工夫で回避できない、WebAuthn の仕様上の制約。

### 影響

1. **本番ドメインを、ユーザーに公開する前に確定しなければならない**
   - β(M8)でユーザーが Passkey を作った後にドメインを変えると、**全員がログインできなくなる**
   - リカバリーコードでの復帰は可能だが、体験としては事故

2. **Vercel のプレビューURL(デプロイごとに変わる)では Passkey の実機テストができない**
   - → ステージング用に**固定ドメインを1つ**用意する(T-2)

### ROADMAP への変更提案

| 項目 | 現在 | 変更後 |
|---|---|---|
| 「サービス名の商標・ドメイン確認」 | 並走レーン / S3完了まで | **S1 のブロッカー / S1開始前まで** |

理由: S1 で Passkey を実装した時点でステージングにデプロイして実機検証したい。そのためにドメインが要る。ドメインは商標確認の結果に依存する。

## 5. スパイクコードの扱い

`src/app/spike/` および `src/lib/spike-session.ts` は **S1 で削除する**。

- チャレンジ・公開鍵の Cookie 保持(T-10)は、インフラなしで実機検証に到達するための一時的な手段
- S1 で `credentials` / `sessions` テーブル(データモデル §2)へ置き換える
- 検証ロジック(`generateRegistrationOptions` の設定値など)は S1 の本実装へそのまま引き継ぐ

削除時に本ドキュメントへ「S1で置き換え済み」と追記すること。
