# データの所在 — サーバー保存とE2EEの設計判断

> **People OS 全体にかかる判断**([位置づけ](./07-positioning.md))。
> 保存の方針は機能ごとに変えられないので、プラットフォーム側の文書として置く。

**Version 0.1 / 2026-09-06**

「情報を管理されない」を実現する手段として、**メッセージをサーバーに保存しない構成は成立するか**を検討した記録。

結論は **[D-17](./01-screen-design.md#d-17-サーバーに保存しないではなくサーバーが読めないを目指す)**。
仕様書側には要約だけを置き、根拠は本書に持たせる。

---

## 結論

> **「サーバーに保存しない」ではなく「サーバーが読めない」を目指す。**
> 保存期間は Connection の寿命に縛る。完全P2Pは対面セッションに限定して検討する。

理由は3つ。

1. **憲法が要求しているのは非保存ではなく E2EE** — 「保存していない」はユーザーから検証できず、
   結局「企業を信じてください」に帰着する。第十一条が唯一否定していることになる(§2)
2. **非保存は憲法第三条・第六条と正面衝突する** — 端末に閉じたデータは機種変更で消え、
   持ち出す先もない(§2)
3. **期限付き Connection は「保存期間 = 関係の寿命」を自然に書ける** — 関係に終わりがある
   プロダクトにしか書けない仕様であり、実装コストもほぼゼロ(§4)

---

## 1. 「サーバー保存なし」には4段階ある

同じ言葉で全く違うものを指せてしまうので、まず分ける。

| # | 方式 | サーバーが持つもの | 非同期送信 | 通知 | 機種変更 | 検証可能性 |
|---|---|---|---|---|---|---|
| ① | **完全P2P**(WebRTC DataChannel)| 接続の仲介(SDP/ICE)のみ | ✕ 同時オンライン必須 | ✕ | ✕ 消える | △ |
| ② | **リレー**(通すが書かない)| 一瞬だけメモリ上 | ✕ 同じ | ✕ | ✕ 消える | **✕** |
| ③ | **E2EE + 期限付き保管** | **読めない暗号文**を配信まで | ○ | △ | ○ | ◎ |
| ④ | **E2EE + 長期保管** | 読めない暗号文をずっと | ○ | ○ | ○ | ◎ |

現状(MVP)はこの表の**外側**にある — サーバーが平文を持つ([D-9](./01-screen-design.md))。

### ②の検証可能性が ✕ である理由

「保存していません」は**ユーザーから確かめられない**。
ソースを公開しても、いまサーバーで動いているコードがそれである保証はない。
③④は「保存されていても読めない」ので、確かめる必要がそもそも無い。

この差が §2 の結論をそのまま決めている。

---

## 2. 憲法との照合 — ①②は憲法違反の側に落ちる

| 条 | ① 完全P2P | ③④ E2EE |
|---|---|---|
| 第一条 主権はユーザーにある | ○ | ○ |
| 第二条 企業は最小限しか知らない | ○ | ○ |
| **第三条 どの端末でも自分である** | **✕ 端末を変えたら消える** | ○ |
| 第五条 段階的な公開 | ○ | ○ |
| **第六条 削除・持ち出し・移行** | **✕ 持ち出す先がない** | ○ |
| 第七条 シンプルであること | ✕ 鍵管理がユーザーに降りる | △ |
| **第十一条 企業を信じなくてよい** | **✕ §1のとおり満たせない** | ◎ |

**憲法が指しているのは非保存ではなく E2EE。**

第三条「通信は端末ではなく、人に属する」は、端末にデータを閉じ込める設計の**否定**として読める。
①②はこの条を破って第十一条も満たせないので、思想の強化ではなく後退になる。

### D-9 の位置づけを改める

[D-9](./01-screen-design.md) は「マルチデバイス鍵同期が複雑なのでE2EEはPhase 3」と書いてあり、
**「難しいから後回し」**に読める。本書の検討により、正しくは
**「第十一条を満たす唯一の手段。やるかどうかではなく、いつやるかの問題」**である。
D-9 の記述をこの趣旨に更新した。

## 3. 弊害(深刻な順)

### 3-1. 【致命的】通報・安全機能が成立しない

現状の `reports` は「**明示同意があるときだけ**直近20件の本文を運営に提供する」設計で、
同意なしの証跡混入を CHECK 制約で書き込めなくしてある(`reports_evidence_needs_consent`)。

サーバーに本文が無ければ、この証跡が**作れない**。
ハラスメント対応ができないプラットフォームになる。βで1件起きた時点で詰む。

**解ける**(§5)。ただし設計を足す必要がある。

### 3-2. 【致命的】通知が出せない → 「日常で使う」と正面衝突

①②では相手がオフラインなら通信自体が存在しないので、原理的に通知できない。

③④でも本文入りの通知には**端末側での復号**が要る。
Web Push なら Service Worker で復号できるが、鍵が IndexedDB から読める場所にある必要があり、
XSS の被害範囲が「セッション奪取」から「**全履歴の復号**」に広がる。

### 3-3. 【重い】非同期性の喪失(①②)

メッセージングの本質は「相手がいなくても送れる」こと。
同時オンラインが必須なら、それは通話に近いものであってチャットではない。

### 3-4. 【重い】鍵を失うと復旧不能

「リカバリコードを控えてください」を一般生活者に要求することになる。
Passkey を見送った([D-7](./01-screen-design.md))のと**同じ壁**に当たる。

### 3-5. 【中】その他

| 項目 | 内容 |
|---|---|
| NAT越え失敗(①)| 1割前後で直接接続できず TURN 中継が要る。TURN を運営する時点で「サーバー不要」ではなくなる(暗号化されていれば読めないが)|
| サーバー側検索が不可能 | 端末内検索のみになる |
| 実装難度 | **暗号は自前実装しない。** 1対1は Signal Protocol(libsignal)、グループは MLS(RFC 9420)。マルチデバイス鍵同期が最難所 |
| スパム対策 | 内容を見ない前提のレート制限・評判ベースに寄せる必要がある |

### 3-6. 利点(公平に書いておく)

- 法的な開示要請に「持っていないので出せない」と答えられる
- 侵害されても漏れるものがない
- 「削除しました」が主張ではなく事実になる(憲法第六条・第十一条)

## 4. People OS だけが書ける仕様 — **保存期間 = Connection の寿命**

他社が E2EE をやっても ④(暗号文を永久に持つ)にしかならない。**関係に終わりがないから**。

People OS には**期限付き Connection** がある。だから ③ が自然に書ける。

```
7日Connection      → サーバーの暗号文も7日で消える
継続                → 期限が伸びれば保管も伸びる
終了                → 全部消える
恒久化を選んだ関係    → そこだけが残る
```

**「消えるのが既定、残るのが選択」。**

- 仕様として一行で説明できる
- 思想(構想書 §9 / 憲法第六条)と1対1で対応する
- **実装コストがほぼゼロ** — `ON DELETE CASCADE` は既に張ってあり、
  消す場所(`advanceExpiries()`)も既にある

E2EE を待たずに**いますぐ**できる。これが §7 の第1段階。

## 5. 通報をどう成立させるか(E2EE後)

サーバーが本文を持たなくなったとき、`reports.evidence` は次の形に置き換える。

```
1. 送信時、送信者の秘密鍵で本文に署名する(公開鍵はサーバーが配布)
2. 受け手の端末は、受信したメッセージと署名を端末内に保持する
3. 通報時、受け手が「この会話を添える」を選んだときだけ、
   端末から平文+署名をアップロードする
4. 運営は署名を検証する — 改ざんされた証跡は弾ける
```

- **同意があるときだけ本文が出る**という現在の性質は保たれる(むしろ強くなる。
  同意が「サーバーにあるものを使う許可」から「端末から送る操作」になるため)
- 取り消し済みメッセージは受け手の端末からも消えるので、証跡に含みようがない([D-12](./01-screen-design.md))
- 署名がないと「相手が言っていないことを捏造した通報」が可能になる。**署名は必須**

## 6. 完全P2Pを使える唯一の場面 — 対面セッション

①の弊害(§3-2 / 3-3)が**全部消える場面が1つだけある**。

QRで会った直後 — **両者が同じ場所にいて、両方の画面が開いている**。

| ①の弊害 | 対面では |
|---|---|
| 非同期に送れない | 要らない(目の前にいる)|
| 通知が出せない | 要らない(画面を見ている)|
| 履歴が残らない | 要らない(その場の会話)|
| 機種変更で消える | 関係ない(いまの話)|

しかも「**その場の会話は残らない**」は思想として一貫している。
P2Pが張れなければ通常のConnectionに落とせばよく、失敗コストもない。

これを「**その場かぎりモード**」として §7 の第2段階に置く。

> ⚠️ ただし §3-1 は消えない。その場かぎりモードの会話は通報の証跡にできない。
> 「このモードの会話は通報に使えません」と**明示する**か、
> 受け手側だけ一時保持するかを、実装前に決めること。

## 7. 進め方

| 段階 | 内容 | コスト | 時期 |
|---|---|---|---|
| **第1** | Connection終了時に本文を物理削除。「**保存期間 = 関係の寿命**」を仕様に明記 | **小** — 既存の仕組みで足りる | いつでも |
| **第2** | 対面セッションのみP2P(その場かぎりモード)。通報の扱いを先に決める | 中 | Phase 2 |
| **第3** | E2EE + TTL(③)。libsignal / MLS。通報は §5 の署名付き端末提出に変更 | 大 | Phase 3([D-9](./01-screen-design.md))|

**順番が重要。** いまやるべきは「保存しない」ではなく「**保存期間を関係に縛る**」。
これだけで「情報を管理されない」の実質はかなり達成でき、
しかも憲法第三条・第六条を犠牲にしない。

---

## 8. やらないと決めたこと(再議論を防ぐための記録)

| 検討したが採らないもの | 理由 |
|---|---|
| **② リレー方式**(通すが書かない)| 検証不可能で第十一条を満たせない。①②の弊害を全部背負って利点だけ無い |
| **①を1対1チャット全体に適用** | 第三条・第六条違反。非同期性を失いメッセージングでなくなる |
| **E2EEを諦めて現状維持** | 第十一条は「いつか」ではなく必達。D-9 は時期の判断であって可否の判断ではない |
| **暗号プロトコルの自前実装** | 間違えると意味がゼロになる領域。libsignal / MLS を使う |
