# PersonalLink 技術選定メモ

**Version 0.1 / 2026年8月**(S0 成果物)

[画面設計書(MVP仕様書)](./01-screen-design.md) と [データモデル](./02-data-model.md) を実装するための技術判断。

判断は **T-1〜T-11** として記録する。仕様の設計判断(D-x)と同じく、**迷ったらここが根拠**になる。

---

## 0. 選定の判断軸

構想書と憲法から、この順で優先する。

1. **憲法第二条(最小収集)を技術的に守れるか** — 「収集しない」をコードとスキーマで担保できる構成か
2. **全端末ログアウト・削除を即時に実行できるか**(憲法第一条・第六条)
3. **実機での検証ループが速いか** — Passkey も QR もカメラも、実機でしか本当の確認ができない
4. 情報と人材の入手性(1人+AI体制で詰まらないこと)
5. Phase 2(PWA)・Phase 3(E2EE)への移行を塞がないこと

「速さ」「安さ」は5番目以降。MVPの規模では差が出ない。

---

## T-1. フレームワーク: Next.js 16(App Router)+ TypeScript strict

**選定**: Next.js(App Router / React 19)、`strict: true`。

**理由**
- Phase 1 は Web、Phase 2 で PWA 化。同じコードベースのまま manifest + Service Worker を足せる
- 画面(RSC)とAPI(Route Handlers)を1リポジトリで持てる。1人体制で境界を増やさない
- 情報量が最大。詰まったときに解決が速い(判断軸4)

**却下した案**
- SvelteKit: 軽量で魅力的だが、WebAuthn/PWA周りの実装例が少なく、詰まったときのコストが読めない
- SPA + 別APIサーバー(Fastify等): 構成が正しくても、1人体制ではデプロイ先とCORSとセッションの管理が二重になる

## T-2. デプロイ: Vercel + **固定ステージングドメイン(必須)**

**選定**: Vercel。ただし **ステージング用に固定ドメインを1つ用意する**。

**理由と重要な発見**

> ⚠️ **WebAuthn の Passkey は RP ID(ドメイン)に紐づく。**
> Vercel のプレビューURL(`personallink-abc123.vercel.app`)は**デプロイごとに変わる**ため、
> プレビュー環境で登録した Passkey は次のデプロイでは使えない。
> → **プレビューURLでは Passkey の実機テストができない。**

対策(S1以降の運用として確定):

| 環境 | ドメイン | Passkey実機テスト |
|---|---|---|
| ローカル | `localhost` | 可(WebAuthnは localhost を安全な文脈として許可) |
| **ステージング** | **固定ドメイン1つ**(例 `stg.<本番ドメイン>`) | **可。実機検証はここで行う** |
| プレビュー(PR毎) | 可変URL | **不可**(UI確認とVirtual AuthenticatorのE2Eのみ) |
| 本番 | 本番ドメイン | 可 |

**この判断が生む依存**: 本番ドメインを **S1 開始前に確定**する必要がある。RP ID を後から変えると**既存ユーザーの Passkey が全て無効になる**ため、ドメイン変更は実質不可能。
→ ROADMAP 並走レーンの「商標・ドメイン確認」を **S1 のブロッカー**に格上げする(§ 変更提案)。

## T-3. データベース: PostgreSQL(Neon)+ Drizzle ORM

**選定**: PostgreSQL、ホスティングは Neon、ORM は Drizzle。

**なぜ Drizzle か(Prisma ではなく)**

我々のデータモデルは、**不変条件をDB制約で守りたい**ものが多い。

- 「同一ペアの生きた Connection は最大1つ」→ **部分UNIQUEインデックス**
- 「`expires_at = NULL` ⟺ `status = permanent`」→ **CHECK制約**
- 「1つの Connection に必ず2行の connection_members」→ 制約 + アプリ層

Prisma はこれらの表現が弱く、生SQLのエスケープハッチに逃げることになる。Drizzle はマイグレーションがそのままSQLとして読め、制約を素直に書ける。**「不変条件はアプリのif文ではなくDBに刻む」**という方針(データモデル§3)と相性が良い。

**なぜ Neon か**: Vercel との統合、そして **DBブランチング**。プレビュー環境ごとにDBを分岐できるので、破壊的なマイグレーションを本番と隔離して試せる。

**却下**: Supabase(認証機能が主価値だが、我々は Passkey 自前なので過剰。使わない機能の分だけ理解コストが増える)。

## T-4. 認証: SimpleWebAuthn + **自前のサーバー側セッション**(Auth.js は使わない)

**選定**: `@simplewebauthn/server` / `@simplewebauthn/browser` v13 + 自前セッション。

**なぜ Auth.js(NextAuth)を使わないか**
- Auth.js はメールアドレスまたはOAuthプロバイダを前提に設計されている。**我々は電話番号もメールも持たない**(D-7)。骨格が合わない
- 何を保存しているかを完全に把握できることが憲法第二条の担保になる。ライブラリの内部テーブルに「知らないうちに何か入っている」状態を避ける

**セッションは JWT ではなく DB セッション(重要)**

> MVP必須機能⑩「**全端末ログアウト**」を満たすには、サーバー側で即時 revoke できる必要がある。
> JWT(ステートレス)は発行後の無効化ができず、この要件と**原理的に両立しない**。

→ `sessions` テーブル + HttpOnly / Secure / SameSite=Lax Cookie(セッションIDのみ)。
毎リクエストでDB照合する(Connection一覧などは元々DBを引くので、追加コストは実質ない)。

## T-5. リアルタイム: ポーリング → SSE(WebSocketは採らない)

**選定**: Phase 1 は**3秒ポーリング**で開始し、動作確認後に **SSE(Server-Sent Events)** へ移行。

**理由**
- MVPのチャットは1対1中心。**サーバー→クライアントの片方向**で足りる(送信は通常のHTTP POST)。双方向のWebSocketは要件過剰
- SSE は HTTP のまま扱え、再接続がブラウザ標準で入る。Vercel のサーバーレス環境とも折り合いがつく
- 仕様書§8の方針(まずポーリング→SSE/WS)どおり。**確実に動くものを先に作る**

**注意**: Vercel の Function 実行時間上限に留意。SSE 接続は一定時間で切って再接続させる設計にする(クライアント側は EventSource の自動再接続に任せる)。

## T-6. ファイルストレージ: Vercel Blob(抽象化1枚を挟む)

**選定**: Vercel Blob。ただし `lib/storage.ts` に薄いインターフェースを置き、R2等へ移行可能にする。

**アクセス制御(重要)**
- **公開URLを使わない。** 画像・ファイルは毎回サーバーが**短命の署名付きURL**を発行する
- 発行前に必ず `level_grants(level=2, revoked_at IS NULL)` を検証(データモデル不変条件2)
- 「レベルを下げたのに古いURLで見え続ける」を防ぐため、署名URLの有効期限は**短く(数分)**する

## T-7. テスト: Vitest(単体・結合)+ Playwright(E2E)

**選定**: Vitest + Playwright。プロトタイプ検証で Playwright は既に使用中。

**WebAuthn の自動テストは可能**

> Playwright の **CDP Virtual Authenticator**(`WebAuthn.addVirtualAuthenticator`)で、
> Passkey の登録・認証を**CIで自動テストできる**。

→ 実機確認は「本当に指紋/FaceIDで通るか」の最終確認に絞り、回帰はCIで自動化する。これで実機テストの負荷(ROADMAPリスク「1人体制での実地テスト負荷」)が下がる。

**優先してテストで守るもの**(仕様の性質上、バグると思想が壊れる箇所)
1. 継続選択 `end` が相手のAPIレスポンスに一切出ないこと(D-3)
2. 期限到達前に「継続しない」で早期終了しないこと(タイミングリーク)
3. silent block で送信APIが正常応答を返すこと(D-3同思想)
4. 取り消し済みメッセージの本文・添付が通報証跡にも含まれないこと(不変条件9)

## T-8. 期限エンジン: Vercel Cron + 読み取り時の遅延評価(二重化)

**選定**: データモデル §connections の方針どおり二重化する。

- **Cron**(定期): 状態遷移・期限24h前通知のトリガ
- **遅延評価**(読み取り時): Connection を読むたびに `expires_at` を評価して状態を導出

**なぜ二重化が効くか**: Cron が遅延・失敗しても、ユーザーが画面を開いた時点で正しい状態が表示される。**Cronの実行間隔の精度に、ユーザー体験が依存しない**。

**コスト注記**: Vercel Cron の分単位実行は有料プラン。無料枠では1日1回。→ 遅延評価があるため MVP は粗い間隔でも成立するが、期限通知の精度は落ちる。**S4 でプラン判断が必要**(オーナー判断事項)。

## T-9. 「収集しない」の技術的担保

憲法第二条を運用で守るのではなく、**構成で守る**。

| 守ること | 実装 |
|---|---|
| 本文をログに残さない | 構造化ログに `body` を渡さない lint ルール + ログ関数側でのフィールド遮断 |
| エラー監視に本文を送らない | Sentry等を入れる場合 `beforeSend` で本文・添付URLを除去。**S0時点では監視SaaSを入れない**(入れるときに別途判断) |
| 計測に本文を含めない | イベント送信関数の引数型をメタデータのみに制限(型で防ぐ) |
| アクセスログにトークンを残さない | QRトークン・セッションIDをURLに載せない(常にPOSTボディ/Cookie) |

## T-10. スパイクの構成: **Cookieベースのステートレス実装**(S0限定)

WebAuthn スパイクを「DBを用意しないと動かない」ものにすると、実機テストまでの距離が遠くなる。

**判断**: S0 のスパイクは **チャレンジと公開鍵を署名付き HttpOnly Cookie に保持**し、**DB不要で動く**ようにする。

- 公開鍵は秘密情報ではないため Cookie 保持で問題ない
- サーバーレスの複数インスタンス間で状態を共有できない問題も回避できる
- **S1 で `credentials` / `sessions` テーブルへ置き換える**(スパイクコードは破棄前提。`src/app/spike/` 配下に隔離)

---

## T-11. 採用しないもの(現時点)

| 技術 | 理由 |
|---|---|
| 監視SaaS(Sentry等) | 本文流出リスクの設計を先に固めてから。S0では入れない(T-9) |
| CSSフレームワーク(Tailwind等) | GLASS-HUD は CSS変数(`--glass`)とclip-path主体。ユーティリティCSSと相性が悪い。素のCSS Modulesで足りる |
| 状態管理ライブラリ | RSC + URL状態で足りる規模。必要になってから入れる |
| Docker | Vercel + Neon で開発〜本番が揃うため、現時点では複雑さが増えるだけ |
